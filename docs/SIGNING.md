# Signed packages

`pkg` will not read a package index it cannot authenticate. The index is
signed with Ed25519, the signature is checked against a public key that is
part of the OS image, and every package tarball is checked against the
sha256 recorded in that signed index before anything is unpacked.

Nothing in this design is a placeholder: the signer, the verifier, the
refusal paths and the tests are all in the tree and are quoted at the end
of this document.

---

## 1. What signing buys you

The repository is served over plain HTTP(S) from a server nobody in this
project controls, and `pkg` runs as root. Without a signature, a hostile
network or a hostile mirror rewrites `index.tsv`, and the sha256 column is
worthless: the attacker supplies both the sha256 and the tarball. With a
signature:

* **A tampered index is rejected.** One changed byte in `index.tsv` makes
  verification fail and `pkg` refuses the whole file (proof in §7).
* **A hostile mirror cannot substitute packages.** It can serve any bytes
  it likes; the index it would have to forge is signed.
* **The tarball gate becomes meaningful.** The sha256 in the signed index
  is the publisher's statement about the bytes; `pkg` compares the
  download against it and deletes a mismatch instead of unpacking it.

### What it does **not** buy you

These are the honest limits, not a wish list:

* **Whoever can replace the public key can sign anything.** The key lives
  at `/etc/mystic/repo.pub` inside the boot image. There is no secure-boot
  chain in Mystic OS: an attacker who can rewrite the boot medium can
  replace the key and the packages together. The signature protects the
  network path and a compromised mirror, not a compromised image.
* **A stolen signing key is a full compromise until the key is rotated and
  a new image is distributed.** Keep the seed off the network.
* **No rollback protection.** An old, correctly signed `index.tsv` still
  verifies. There is no timestamp, expiry or monotonic version in the
  format, so an attacker who controls the mirror (or the clock) can serve
  yesterday's index and its old packages. Fixing that needs a signed
  timestamp with a freshness window, which this format does not have.
* **One signature covers all rows.** There is no per-package signature;
  the index is the signed unit, and every tarball is covered through the
  sha256 it lists.
* **The `size` column is informational.** `pkg` uses it to print
  "installing web (1.2 MB)", and it is part of the signed bytes, but the
  enforcement is the sha256, not the size.
* **Availability is not protected.** An attacker can still block, delay or
  404 the repository. That is a denial of service, not a forgery.
* **The Store's browsing list is still unauthenticated.** Installation is
  gated (the Store only asks for a *name*, and `pkg install` re-verifies the
  index before it looks that name up), but the rows the Store *shows* come
  from a plain `wget` copy of the index written by the desktop. See section
  5 for the exact lines and the one-line fix, and section 8 for the risk.

## 2. Repository layout

```
<base>/index.tsv        name<TAB>version<TAB>size<TAB>sha256<TAB>file<TAB>description
<base>/index.tsv.sig    64 raw bytes: R || S, little-endian
<base>/index.pub        32 raw bytes: the publisher's public key (for humans)
<base>/<file>           the package tarballs named in the index
```

The signature covers the **exact bytes** of `index.tsv` — trailing newline
included. It is not a signature over a parsed form, so any reformatting of
the file (even reordering whitespace) invalidates it.

`index.pub` is published so a person can compare the key fingerprint with
the one the publisher quotes. `pkg` itself never downloads it: a key that
arrives from the same server as the signature proves nothing.

## 3. The trust anchor

```
/etc/mystic/repo.pub     32 raw bytes (or 64 hex digits + newline)
```

This file ships in the image, is listed in no settings/persistence path,
and is never written by any app. It is the only key `pkg` trusts.

The key currently in the tree (generated by `tools/sign-index.py keygen`):

```
file        : stage/etc/mystic/repo.pub   (installed at /etc/mystic/repo.pub)
public hex  : ede5d32a05be2b79f9535f8945e35e90e2d21f143ec9326babcf424ee4cba41f
fingerprint : sha256 ce177b2cc56f3cfd4c3458a7e7201eece66b45b01a1a888b9a6f1e4cbcf90096
```

The matching seed is **not** in the repository; it was written to
`build/sign/repo.key` (mode 0600), which `.gitignore` excludes (`build/`).

**Important:** that makes the checked-in key a *development* key. Before
any release, generate a fresh pair on the publisher's machine, commit the
new public half to `stage/etc/mystic/repo.pub`, rebuild the image, and keep
the seed offline:

```sh
tools/sign-index.py keygen --seed ~/secure/mystic-repo.key \
                           --pub stage/etc/mystic/repo.pub
```

`keygen` refuses to overwrite an existing seed without `--force`, so a
mistyped command cannot destroy the publishing key.

To inspect what this image trusts:

```
$ pkg key
repository key: /etc/mystic/repo.pub
  sha256   : ce177b2cc56f3cfd4c3458a7e7201eece66b45b01a1a888b9a6f1e4cbcf90096
  raw bytes: ede5d32a05be2b79f9535f8945e35e90e2d21f143ec9326babcf424ee4cba41f
compare that sha256 with the fingerprint the publisher quotes;
if they differ, packages from that publisher will be refused.
```

`pkg repo` also prints the key path and fingerprint next to the index
state, so a support question can always be answered from the machine.

## 4. Publisher workflow

```sh
# once
tools/sign-index.py keygen --seed build/sign/repo.key \
                           --pub stage/etc/mystic/repo.pub

# every time the index changes
tools/sign-index.py sign  --seed build/sign/repo.key \
                          --in  build/repo/index.tsv \
                          --pub stage/etc/mystic/repo.pub

# confirm exactly what pkg will do
tools/sign-index.py verify --pub stage/etc/mystic/repo.pub \
                           --in  build/repo/index.tsv
```

`sign` writes `<in>.sig` (64 raw bytes) next to the file. `--pub` is not
decoration: it makes the signer read the public half that will be
distributed and **refuse to sign** if the seed does not match it, which is
the failure mode where an image silently trusts a key nobody has.

`tools/serve-repo.sh` builds the index, signs it with
`$REPO_KEY` (default `build/sign/repo.key`) against `$REPO_PUB`
(default `stage/etc/mystic/repo.pub`), copies the public key to
`index.pub`, and prints a warning instead of producing a silently unsigned
mirror when no key is present.

**Rotation.** Generate a new pair, put the new public key in
`stage/etc/mystic/repo.pub`, rebuild and redistribute the image, then
re-sign the repository. Machines running the old image will keep rejecting
the new index — that is the intended behaviour, and the reason the key must
be distributed with the OS rather than fetched.

## 5. What `pkg` does, in order

`fetch_index` in `stage/usr/bin/pkg`:

1. `prepare_cache` — refuses a cache directory (`/tmp/pkg`) owned by a
   different uid, because a directory an unprivileged user can write would
   allow the index to be swapped between the signature check and the read.
2. Download `index.tsv` to `index.tsv.part`.
3. `index_ok` — reject an HTML error page / a file that is not a TSV.
4. Download `index.tsv.sig` to `index.tsv.sig.part`. **A missing signature
   is a refusal**, not a warning.
5. `verify_index` — run `/usr/bin/ed25519-verify /etc/mystic/repo.pub
   index.tsv.part index.tsv.sig.part`. Any non-zero exit means: delete both
   parts and leave the previously verified index untouched.
6. Only then move the pair into place, and re-verify the pair in its final
   location before reporting the package count.

`ensure_index` re-verifies a **cached** index on every use, so a file in
`/tmp` that cannot be authenticated is treated as absent and refetched.

`cmd_install` then:

1. Takes the row from the verified index; the sha256 column must be 64 hex
   characters and the file name must be a bare file name (no `/`, no
   leading dot).
2. Downloads the tarball, or reuses a cached copy **only** after its sha256
   matches the signed value. A cached file that does not match is deleted
   and downloaded again.
3. After the download, `sha256sum` must equal the signed value or the file
   is deleted and the install dies — it is never unpacked.
4. `tar_members_ok` — list the archive and refuse absolute members and
   `..` path components before extracting anything, because `tar` extracts
   as root and would happily write outside the install directory.
5. Unpack into `$APPS/.<name>.new.$$`, then swap it in, so a failed upgrade
   leaves the working installation alone.

The user-visible refusals are specific, e.g.:

```
pkg: SIGNATURE VERIFICATION FAILED for /tmp/pkg/index.tsv.part
pkg:   key       : /etc/mystic/repo.pub
pkg:   fingerprint: sha256 ce177b2cc56f3cfd4c3458a7e7201eece66b45b01a1a888b9a6f1e4cbcf90096
pkg:   signature : /tmp/pkg/index.tsv.sig.part
pkg: the index was altered in transit, or it was signed with a key this
pkg: image does not trust. Either way it is not used.
pkg: the index from ... was NOT installed; any previously verified
pkg: index in /tmp/pkg/index.tsv is left untouched
```

```
pkg: checksum mismatch for demo.tar.gz (signed index says 584e4395..., download is 6635227c...) - refusing to unpack
```

```
pkg: evil1.tar.gz contains a path that would escape the install directory: ../escaped
pkg: evil1.tar.gz is not safe to unpack - nothing was installed
```

Everything is **fail closed**: a missing key, a missing verifier, a missing
signature, a bad signature, a bad sha256 and an unsafe archive all stop the
install. There is no `--insecure` flag.

### The Store's copy of the index is not authenticated yet

`pkg` writes its verified index to `/tmp/pkg/index.tsv` and also copies it
to `/run/mystic/repo.index` (`stage/usr/bin/pkg:319-321`). The Store window
does not read `pkg`'s copy: it reads `/run/mystic/repo.index`
(`src/apps/store.c:163`, opened at `:741` and `:755`), and the desktop
overwrites that file with a plain, unverified
`wget -q -T 10 -O /run/mystic/repo.index http://10.0.2.2:8000/index.tsv`
on first run (`src/main.c:1854-1857`) and on every Refresh
(`src/main.c:1865-1868`). Nothing on that path checks a signature.

Consequence: the Store's *list* - names, versions, sizes, descriptions,
the installed/update hints - is attacker-chosen on an untrusted network.
Installing is still gated: the Store writes only the chosen *name* to
`/run/mystic/install.request` (`src/apps/store.c:1590`), the desktop
validates it (`src/main.c:404-422`) and `pkg install` re-fetches and
re-verifies the signed index before it looks the name up, refusing one
that is not there (`stage/usr/bin/pkg:325-336`, `:421`). So the worst
case today is a misleading row or a denied install, not code execution -
but it is a hole in this story and it is listed in section 8.

The fix belongs in `src/main.c`, which this worker does not own. Either:

1. replace both `wget` commands (`src/main.c:1854-1857` and
   `:1865-1868`) with
   `execl("/bin/sh", "sh", "-c", "pkg update", (char *)NULL);` so `pkg`
   is the only writer of `/run/mystic/repo.index`; or
2. leave the fetch in `main.c` but have the Store read
   `/tmp/pkg/index.tsv` and only after `ed25519-verify` accepts
   `/tmp/pkg/index.tsv.sig` against `/etc/mystic/repo.pub`.

Option 1 is one line per site and makes the Store exactly as trustworthy
as the installer. Until it lands, section 8 carries the risk.

## 6. The verifier

`src/tools/ed25519.c` — one file, no dependencies, no `libcrypto`:

* SHA-512 (FIPS 180-4) implemented in the file, with the length appended in
  the standard 128-bit field.
* Field arithmetic modulo `2^255 - 19` in 16 limbs of 16 bits held in
  signed 64-bit integers (the public-domain TweetNaCl representation),
  which needs no compiler support for 128-bit integers.
* Edwards-curve group law in extended coordinates, a constant-time
  conditional swap, a constant-time 32-byte compare for the final `R`
  check.
* **Canonical `S` is enforced** (`S < L`). Without it `(R, S)` and
  `(R, S + L)` would both verify — signature malleability. The self test
  checks that `S + L` is rejected.
* **Canonical `y` is enforced** for both `A` and `R` (`y < p`). The 32
  bytes `ed ff .. ff 7f` encode `y = p`, which is the same point as
  `y = 0`: without this check one point has several valid encodings.
* **Low-order points are refused** for both `A` and `R` (`[8]P` is the
  identity). Without that test the identity public key "verifies"
  `R = identity, S = 0` for *every* message - a signature that verifies
  under a key nobody holds. Honest signatures never land in the set:
  `R = [r]B` for a uniform `r` does so with probability about 2^-252.
* Both points must be on the curve, and `R` is compared as bytes.
* `--selftest` runs the RFC 8032 section 7.1 vectors 1-3 (a corrupted
  signature for each, a corrupted message for the two non-empty ones, a
  non-canonical `S` for each) and three forged encodings that must all
  be rejected: the `y = p` key, the identity key, and a low-order `R`.

It is built by `tools/build-desktop.sh` and installed as
`/usr/bin/ed25519-verify`:

```sh
zig cc -target x86_64-linux-musl -Os -static -Wall -Wextra \
    -Wno-unused-parameter -o build/ed25519-verify src/tools/ed25519.c
cp build/ed25519-verify stage/usr/bin/ed25519-verify
```

Interface:

```
ed25519-verify <pubkey> <message> <signature>
  pubkey    : 32 raw bytes or 64 hex digits
  signature : 64 raw bytes (R || S)
exit 0 valid, 1 invalid, 2 usage / unreadable file
```

`tools/sign-index.py` is a **second, independent** implementation of the
same algorithm (the RFC 8032 reference model: recursive extended-coordinate
arithmetic written differently, a different scalar-reduction path, and a
Python `pow()`-based inversion). The two are cross-checked against each
other on random inputs, so a bug would have to occur identically in two
independently written implementations to pass.

### Forged *encodings* are rejected too, not just forged bytes

A verifier that only tests curve membership accepts signatures that were
never signed. Both cases below returned **exit 0** against the earlier
build (`pt_unpack_neg` with no canonical-`y` and no low-order test):

```
# the two forged encodings, built from bytes so nothing here is magic
$ python -c "open('pk_y_eq_p.bin','wb').write(bytes.fromhex('ed' + 'ff'*30 + '7f'))"
$ python -c "open('pk_identity.bin','wb').write(bytes([1]) + bytes(31))"
$ python -c "open('sig_y_eq_p.bin','wb').write(bytes([1]) + bytes(63))"
$ python -c "open('sig_identity.bin','wb').write(bytes([1]) + bytes(63))"
$ printf "forged under a non-canonical key" > msg1.txt
$ printf "forged with the identity key"     > msg2.txt

# the earlier build, which tested only curve membership:
$ ed25519-verify pk_y_eq_p.bin   msg1.txt sig_y_eq_p.bin   ; echo exit=$?
exit=0          <-- y = p accepted as a key
$ ed25519-verify pk_identity.bin msg2.txt sig_identity.bin ; echo exit=$?
exit=0          <-- identity key accepted

# today:
$ ed25519-verify pk_y_eq_p.bin   msg1.txt sig_y_eq_p.bin   ; echo exit=$?
invalid
exit=1          <-- y >= p is not a canonical key encoding
$ ed25519-verify pk_identity.bin msg2.txt sig_identity.bin ; echo exit=$?
invalid
exit=1          <-- the identity key is low-order
$ ed25519-verify --selftest
selftest: ok
```

Those three cases are now compiled into `--selftest` (including the
low-order `R`), so the property is enforced by a test rather than
asserted in prose, and `.work/sign/crosscheck.py` feeds the same three
encodings to both implementations and requires both to reject them.

### Test coverage actually run

* `.work/sign/pkgtest.sh` — **22 checks, 0 failures** against the real
  `stage/usr/bin/pkg`: signed index accepted; one flipped bit refused and
  the cached index left intact; missing signature refused; foreign key
  refused; verified install works; corrupt tarball refused and nothing
  unpacked; `../` member refused; absolute-path member refused; missing
  key refused; missing verifier refused.
* `.work/sign/crosscheck.py` — **0 failures** in every run (the check count varies with how many random messages happen to be empty; each run does well over 250) comparing
  `src/tools/ed25519.c` with `tools/sign-index.py` over random keys and
  messages: valid signatures accepted, one-bit signature flips rejected,
  one-bit message flips rejected, wrong key rejected, uniformly random
  64-byte signatures rejected.
* `tools/serve-repo.sh --index` — the real publisher path: it packed the
  eight app bundles, signed the 1112-byte index with the development

  (`8 packages (signature ok, ...)`) and installed one of them with a

* `ed25519-verify --selftest` — RFC 8032 vectors 1-3 plus a corrupted
  signature each, a corrupted message for the two non-empty vectors, a

* `python tools/sign-index.py selftest` — the same vectors through the

`--selftest` is compiled into the shipped binary, so the target system can
be checked with one command:

```
$ ed25519-verify --selftest

```

## 8. Residual risks, ranked

| Risk | Consequence | Mitigation |
|---|---|---|
| Boot medium rewritten | Attacker replaces `/etc/mystic/repo.pub`, then signs anything | Not mitigated: no secure boot. Signing protects the network, not the image. |
| Signing key stolen | Attacker publishes packages every image trusts | Rotate the key, ship a new image. No revocation path exists in this format. |
| Replay of an old signed index | User installs an older package with a real vulnerability | Not mitigated: no expiry/timestamp. |
| Mirror blocks or delays | Installs fail | Expected; availability is not a security property here. |
| Cache directory pre-created by uid 1000 | Index swapped between check and read | `prepare_cache` refuses a foreign-owned cache; `/tmp/pkg` is root-owned 0755. |
| `tar` extracting as root | Files written outside the install dir | `tar_members_ok` rejects absolute and `..` members before extraction. |
| Store "Available" list is unauthenticated | Names, versions, sizes and descriptions shown in the Store are attacker-chosen over plain HTTP; installs are still gated because `pkg` re-verifies before looking up the name | **Not mitigated yet**: `src/main.c:1854-1857` and `:1865-1868` write `/run/mystic/repo.index` with plain `wget`. Make `pkg update` the only writer, or have the Store verify before reading (see section 5). |

## 9. Host and CI notes

`pkg` can be exercised outside the image with three environment variables,
which exist for testing and are **not** a security boundary (anyone who can
set them can edit the script):

| Variable | Default | Purpose |
|---|---|---|
| `MYSTIC_REPO` | from `/etc/mystic/repo.conf` | repository base URL |
| `MYSTIC_REPO_PUB` | `/etc/mystic/repo.pub` | trust anchor |
| `MYSTIC_VERIFY` | `/usr/bin/ed25519-verify` | verifier binary |
| `MYSTIC_CACHE` | `/tmp/pkg` | download cache |
| `MYSTIC_APPS` | `/root/apps` | install root |

A host test therefore looks like:

```sh
MYSTIC_REPO=http://127.0.0.1:8000 \
MYSTIC_REPO_PUB=stage/etc/mystic/repo.pub \
MYSTIC_VERIFY=build/ed25519-verify \
MYSTIC_CACHE=/tmp/pkgtest MYSTIC_APPS=/tmp/pkgapps \
    sh stage/usr/bin/pkg update
```

In the image none of these are set, so the defaults above apply.
